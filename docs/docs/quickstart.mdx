Use Node 24. Clone the owner-authorized repository, then run:

```sh
npm ci
npm run check
npm run dev
```

Open http://localhost:3000. The dev server stays running until Ctrl-C. Restore the
flight example, Suggest design, select the scheduled cache, then Start. Warmup uses
real 15-second HTTP requests. Request either hot key after warmup. Change data and
wait for the later 60-second cadence; observe the new version after refresh completes.
Cancel releases the sandbox. Full lifetime is 120 seconds.

```sh
npm run example:flight
npm run example:http
```

The flight example exits after 120 seconds; the custom inventory service and local
scheduler stay running until Ctrl-C. Both restart cold. For production, place the
scheduler in an always-running service/cron and use a suitable cache; this bounded
single-process alpha does not provide durable jobs or high availability.

```sh
npm run build
npm pack --workspace @plugproject/plug --pack-destination /tmp
```

Install the resulting tarball in a fresh directory outside this workspace with
`npm install /tmp/plugproject-plug-0.2.0-alpha.1.tgz`. Plug is licensed under the
[MIT License](https://github.com/plugproject/plug/blob/main/LICENSE); npm publication
remains disabled.

```sh
npx plug setup                 # optional guided model-provider setup
npx plug setup --check         # non-secret readiness status
npx plug ui
```

Core indexing, analysis and OpenSpec/MCP reads need no environment variables.
The setup prompt writes the selected workspace's ignored mode-`0600`
`.env.local`. Jev needs `TYPESAFE_API_KEY` plus `PLUG_JUDGE_MODEL`; completion
drafting needs an Anthropic or OpenAI key plus `PLUG_DRAFT_MODEL`; design review
reuses the draft provider/model unless `PLUG_REVIEW_PROVIDER` and
`PLUG_REVIEW_MODEL` override them. A binding's `${env:NAME}` header reference
requires that project-specific variable only when the binding executes.

The local workbench serves the same UI on http://127.0.0.1:4319 (loopback only;
`--port` and `--workspace` change the defaults). If the current project is not
indexed it offers to index it; `npx plug index . --out index.json` does the same from
the command line. Review the draft system and the listed gaps, then use it as the
caller or downstream, or add MCP and A2A systems from their servers or imported
metadata.

## Edit the workflow graph

The Workflow section draws each system as a group and its operations as nodes. Each
edge is one connection; its badge shows the top priorities, latency target and, after
analysis, the selected architecture. Select an edge, by its line or badge, to edit what
that connection needs in the inspector beside the canvas: its required experience,
priorities and downstream behavior. The badge's **✎** button jumps to them (on narrow
screens the inspector sits below; **Edit … ↓** jumps to it).

Create elements anywhere. Double-click empty canvas to add a system, or the inside of a
system to add an operation to it. Right-click the canvas, a system, an operation or an
edge for its actions. Hover an operation to show a **+** on each side. Drag the right
one onto any part of an operation of another system to add a connection (the left one
draws it from a caller), or drop the drag on empty canvas to create a new connected
system. Click a **+** instead to pick from every operation it can still call or serve;
pick as many as you need. **+ Add connection** connects by clicking: click the calling
operation, then the operation it calls; Escape cancels. The serialized design has
no fixed count ceiling; the editor keeps documents and execution resource-bounded.

Drag an operation onto another system to move it there, or onto empty canvas to give
it a new system with the same interface. Its connections follow: as when rewiring, a
moved caller loses its mappings and a moved downstream operation's facts become
unknown. The hint while dragging says why a move is refused, for example when it would
join a system to itself. **Move to…** in the operation's menu and the inspector's
**System** selector do the same without dragging.

**×** removes any system, operation or edge, as does Delete on the selected one; an
operation or system takes its connections with it, the canvas says what went, and undo
restores it. While the graph lacks two systems, an operation in every system or a
connection, a notice lists what is missing and analysis and export wait until it is
complete. Double-click, or press F2 on, a system name, operation ID or edge badge to
rename it or set the latency target in place, and drag either end of an edge onto
another operation to rewire it. **↶** and **↷**, or Ctrl/⌘+Z and Shift+Ctrl/⌘+Z, undo
and redo the last 50 changes. **⤢ Fullscreen** gives the editor the whole screen;
Escape returns. Suggest design and compare each connection's architecture frontier.

For a system that exposes its interface, set its **Protocol**, and keep **Direction**
at **Exposes**; the inspector then takes the server's URL — the MCP endpoint, the
agent or Agent Card URL, or the OpenAPI document URL for a plain HTTP service. A
freshly added system focuses this field: index the server before describing it by
hand. In the local workbench, add any request headers the server needs (they are
used for that request and never saved) and press Enter or choose **Discover
tools**, **Discover skills** or **Discover operations**. Plug lists the server's
tools, reads the agent's card or reads the OpenAPI document, without calling
anything, and notes how long its own fetch took — a synthetic observation, not a
production measurement. Pick the system operations you need and apply. The
hosted playground never contacts your servers: paste a tools/list response, Agent
Card or OpenAPI document under **Import MCP / A2A / OpenAPI metadata** instead.

Before a local host is added, Plug explains that every exposed integration point
becomes eligible for inspection. Choose **Add and inspect** to run bounded safe
reads now, or **Add without inspecting** to defer them. The manifest panel shows
vantage, measurement window, sample size, latency and source timestamp evidence
per operation. **Re-inspect** refreshes it. These observations are from your local
workbench, not production measurements or an SLO; writes and unknown-effect
operations are never automatically called.

On an edge, **Facts still needed** lists the declarations the analysis is waiting
on. In the local workbench, **Draft missing facts** can propose an output meaning,
complete contract mappings or an explicitly documented per-minute downstream
quota. Configure `PLUG_DRAFT_PROVIDER`, its API key and an exact
`PLUG_DRAFT_MODEL`. Every proposal must quote the supplied metadata verbatim,
passes mechanical value checks, and is independently cross-checked by Jev when
TypeSafe is configured. Drafting changes nothing: inspect the quote and choose
**Adopt** to make the declaration (or ignore it). Cache permission, workload,
trust, latency and availability are never drafted.

When your required output and the downstream's declared output meaning are
different texts, the strict comparison fails; in the local workbench **Judge
equivalence** records one typed model judgment over exactly those texts (set
`TYPESAFE_API_KEY`, `PLUG_JUDGE_PROVIDER=typesafe` and an exact
`PLUG_JUDGE_MODEL`; `plug ui` loads them from the workspace's ignored
`.env.local`). Jev returns a calibrated Noul and code classifies values at or
above 0.7 as equivalent. Anthropic and OpenAI remain completion-provider
alternatives. The verdict is pinned to the judged strings — edit either and it
no longer applies.

After analysis, compare the deterministic **Engine verdict** with the separate
**Demonstration** record. **Verify as-is** exercises the direct edge and **Verify
selected design** runs a supported seed design against an authorized REST binding,
within the same 120-second and resource limits. A local critic can review the
bounded report, with Jev independently checking typed claims. Review suggestions do
not alter the graph: inspect their exact citations, then explicitly **Adopt** one
engine-admissible architecture or **Clear adoption**. Plug re-checks the pin when
facts change.

**↓ Download OpenSpec** saves the graph as an
[Open Workflow Specification](https://open-workflow-specification.org/) document,
including the analysis when it is current. **↑ Upload OpenSpec** reads such a
document back. A Plug export restores exactly; edited priorities, latency targets,
task order and removed tasks are reconciled. Other workflows are drafted with every
operational fact unknown, and the review lists what you still need to supply before
you replace the graph.

## Share the spec with your IDE agent

In the local workbench, **Write spec to workspace** writes `.plug/`; from the command
line run:

```sh
npx plug spec input.json        # or a workflow.yaml; no argument re-applies .plug/workflow.yaml
npx plug mcp install --ide cursor
npx plug skill install --ide cursor
```

`.plug/workflow.yaml` is the spec of record, next to `design-input.json`,
`design.json`, `design.md` and an `AGENTS.md` guide for coding agents. Reference
`.plug/AGENTS.md` from your own agent instructions if you want agents to read it
first. `plug mcp install` registers `plug mcp` in project-scoped configuration
(`--ide cursor`, `vscode` or `claude`; `generic` prints the entry). The agent can then
read the spec and apply changes through `plug_update_spec`, which validates and
re-analyzes them. When the workflow file changes outside Plug, the workbench flags
it and **Open workspace spec** reviews the edit on the graph. The **Spec history**
panel lists up to 50 content-addressed Plug revisions plus read-only Git history;
opening an old version always flows through review, **Replace workflow**, and an
explicit write. Plug never commits to your repository.

## Adapt your own HTTP API

Copy `examples/your-http-api/input.json`, change both system descriptions and the
connection's explicit mappings, input/output contract, profile and exact keys to
match your service. Earlier `0.1-alpha.2` documents are migrated automatically.
The bundled envelope adapter accepts POST JSON and returns
`{snapshotAt, version, data}`. A declared `RequestBinding` and `ResponseBinding`
can instead map a plain REST API; local non-loopback execution requires explicit
origin authorization, credentials stay in environment variables, and returned data
must match the declared output schema.

```sh
npx plug analyze input.json --out report
npx plug explain input.json
npx plug demo input.json --endpoint http://127.0.0.1:4010/inventory
npx plug probe inventory --workspace .
npx plug verify primary --mode as-is --workspace .
```

With several connections, pass `--connection ID` to choose the one whose runner
configuration is exported or executed. Analyze performs no calls. Demo executes only
the explicitly bound local service.
Exports are `design.json`, `design.md` (with Mermaid), and `runner.json` containing
input/catalog/design hashes. Do not change requirements just to obtain feasibility.
